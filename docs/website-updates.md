# 网站更新

标题旁的 GitHub 图标打开维护者仓库。右上角绿点表示运行提交与仓库最新提交一致，黄点表示有新提交；灰点表示版本未知或检查失败，不能当作已经是最新版本。

每次打开页面只检查一次，成功结果在服务端缓存 5 分钟、失败结果缓存 1 分钟，并合并并发检查。没有前端轮询、定时检查、自动刷新页面或持续查询 GitHub。用户可以手动点击状态检查；提交更新后提供 GitHub Actions 进度链接，完成后手动刷新。

## 启用管理员一键更新

1. 在自己的部署仓库设置已有的 CI/CD：服务器变量、SSH Secrets、`DEPLOY_ENABLED=true` 和 `PUBLIC_ORIGIN`。
2. 在 GitHub 为该仓库创建专用的 fine-grained Token，只授权这个仓库，赋予 **Actions 读写**与 **Contents 读取**权限。不要使用访问所有仓库的日常个人 Token。
3. 管理 → 系统规则 → 网站更新，填写 Token 并开启。该输入只写：保存后清空，不回传明文，数据库保存与 API Key 分开用途的 AES-256-GCM 密文。备份必须保留原加密主密钥。
4. 管理员点击黄色状态点会提交一次 `cd.yml` 工作流。重复点击与并发浏览器不会再次提交同一正在执行的更新。普通访客不能触发更新。

触发器使用 GitHub 官方 [workflow dispatch 接口](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event)。更新继续执行现有类型检查、测试、Docker 与流式接口验证，再备份数据库、迁移并部署；失败沿用已有回滚。网页进程没有 Docker Socket、SSH 私钥或执行任意系统命令的权限。

默认 `UPDATE_REPOSITORY=vow132/wisdom-tree`，`UPDATE_BRANCH=codex/wisdom-tree`。下载后独立部署应将仓库改成**自己的部署仓库**并配置它的 CI/CD。请求附带目标提交与本站域名，工作流在运行测试和部署前检查两者：域名不匹配不会触发别人的服务器部署。

CI 的 `compose.deploy.yml` 从 `.release.env` 传入当前提交。直接运行 Node 或自己构建 Compose 时，需将 `APP_VERSION` 设置为部署源码的完整 40 位 Git 提交；缺少它会显示未知，避免凭空显示绿点。后续版本发布可保留同一 Token；过期、撤销或权限不足时在后台重新填写。

## 失败与请求状态

Token 不完整、第三方接口不可达或目标提交变化时，界面提供错误与手动重试。GitHub 明确拒绝的更新可重新提交；如果网络中断导致无法确认是否已提交，会保留待确认的更新并提供工作流链接，避免重复触发。再次访问或手动检查时才读取任务状态；运行提交已经更新为目标提交后，状态恢复绿色。

后台设置变更与更新请求写入操作记录，Token 不写入审计、调用日志、仓库、浏览器或模型回复。保留账户、树高、金币、肥料、绑定身份和已接受的 API 请求快照。
